# Train Hard — Premium и оплата (TON)

## Текущий план

| | |
|---|---|
| Цена | **1 TON** |
| Период | **30 дней** |
| Тип | разовый платёж, **без автосписаний** |
| Способ | перевод TON на кошелёк проекта |
| Кошелёк | `UQCFlpQJExAvzamuoBazfMw67wBzGXBEWkci0DLQxYw5Yi8a` |

Смена плана — одна правка в `src/premium/premium-config.js`
(`tonAmount`, `periodDays`, `priceLabel`), затем пересборка
(`python3 build.py && python3 build_telegram.py`).

## Как проходит оплата

```
Экран Premium → «Оформить Premium · 1 TON»
   ↓ генерируется код платежа th-xxxxxxxx (комментарий перевода)
TON-лист: адрес + сумма + код + QR + «Открыть в кошельке» (ton://transfer/…)
   ↓ пользователь переводит TON из любого кошелька
«Я оплатил — проверить»
   ↓ приложение ищет входящую транзакцию на адрес проекта
     с комментарием == код и суммой ≥ цены
транзакция найдена → Premium на 30 дней (entitlement, анти-реплей по коду)
не найдена → «Оплата не подтверждена» (можно повторить позже)
```

Проверка транзакции в два режима (итерация 4):
- **клиентский (текущий бандл)**: публичный API toncenter напрямую из Mini App —
  работает уже сейчас, но доверять entitlement'у нельзя (см. ниже);
- **серверный (готов в `server/`)**: `POST /payments/verify {label}` — тот же
  toncenter-поиск выполняет сервер, entitlement хранится в БД, выдать себе
  Premium клиент не может. 5 тестов в `server/test/payments.test.js`.
  Переключение бандла на серверный режим — через `verifyUrl` в
  `src/premium/premium-config.js` (зарезервирован).

QR и ссылка `ton://transfer/<адрес>?amount=<нано>&text=<код>` подставляют
адрес, сумму и комментарий в кошелёк автоматически (Tonkeeper, Tonhub и др.).

## Модель безопасности

- **Адрес кошелька — публичный идентификатор**, не секрет. Приватных ключей,
  seed-фраз и API-ключей в frontend НЕТ (проверяется аудитом, `tools/audit-test.js`).
- **Код платежа (label) — не доказательство оплаты**: он лишь связывает флоу
  с конкретной попыткой. Доказательство — найденная в блокчейне входящая
  транзакция с корректной суммой.
- **Возврат по ссылке ничего не активирует**: легаси-параметры `?th_pay=return`
  очищаются, ставится pending, Premium не выдаётся (тест «Легаси-возврат»).
- **Анти-реплей**: один код = одна активация; повторная проверка применённого
  платежа не продлевает срок.
- Проверка запускается только явным кликом пользователя — фоновых сетевых
  запросов нет (все остальные функции приложения остаются офлайн).

## Ограничения (честно)

- **Frontend-проверка через публичный API — не security boundary**: владелец
  устройства может подделать локальный Premium так же, как и любой localStorage
  (это задокументированное ограничение client-side MVP; реальная защита
  появится с серверной проверкой).
- toncenter без ключа ограничен по частоте — для ручных проверок достаточно;
  при росте нагрузки получите бесплатный ключ (живёт на сервере, не в клиенте).
- Перевод должен содержать **точный код** в комментарии: без кода платёж
  не найдётся автоматически.
- TON волатилен: цена плана в TON фиксирована, в фиате меняется с курсом.
- **Юридическая заметка**: расчёты криптовалютой за услуги в РФ юридически
  ограничены (запрет на приём крипты как средства платежа). Оцените применимость
  для вашей ситуации/юрисдикции; при необходимости верните отключённую
  ЮKassa-схему или RuStore Pay (git-история конфига).

## Будущий backend 2.0

Абстракция сохранена: `PaymentAdapter.verify()` — единственная точка, куда
подставляется серверная проверка. Поток будущего:

```
Payment / RuStore Pay → server (проверка транзакции/подписи) →
trusted entitlement → PremiumManager
```

В конфиге зарезервирован `verifyUrl`: непустой https-URL переключает проверку
на сервер — **серверная реализация готова** (`POST /payments/verify`, см.
`docs/BACKEND.md`); осталось подключить её в бандле.
